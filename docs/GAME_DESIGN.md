# ゲームデザイン

## 全体を貫く原則

**高スコア = 高リスク。** 3つのステージすべてで、安全に立ち回れば簡単にクリアできますが
点はほとんど入りません。得点はリスクを取ったときにだけ大きく伸びます。

| ステージ    | 安全な選択               | リスクのある選択                                 |
| ----------- | ------------------------ | ------------------------------------------------ |
| 遅刻回避    | 生徒から離れて走る       | すれ違いざまギリギリを通る（ニアミス）           |
| パン購入RTA | 落ち着いて確認してタップ | 読んだ瞬間にタップする（速度ボーナス）           |
| 先生回避    | 早めに隠れる             | 覗かれる直前までタップし続ける（リスクボーナス） |

数値はすべて設定ファイルにあります。

- スコアに影響する定数 → `shared/game-rules/v3.json`（**PHP も同じファイルを読みます**）
- 挙動のチューニング → `src/config/stages/*.ts`

---

## 共通のスコアの仕組み

得点イベントはすべて `ScoreManager` を通ります。

```text
ゲームイベント → ScoreManager → メトリクス（整数）→ スコア式 → UI
```

`ScoreManager` はスコアを直接持たず、**メトリクスを積算するだけ**です。表示されるスコアは
常に `computeStageScore(stageId, metrics)` の結果です。これによって、

1. 画面の数字と計算式が絶対にずれない、
2. サーバーが同じメトリクスから同じ値を再計算できる、
3. 表示側がスコアの算術を一切しない。

### 「unit」メトリクス

コンボ倍率や速度ボーナスは、本来その瞬間のタイミングに依存します。そのままではサーバーが
再計算できないので、クライアントが**その場で整数の unit に変換して積算**します。

| メトリクス         | 発生条件                                                                                      |
| ------------------ | --------------------------------------------------------------------------------------------- |
| `comboUnits`       | コンボ n 段目の成功で `min(n-1, 9)`                                                           |
| `speedUnits`       | 正解1問につき `clamp(ceil((2500 - 反応ms) / 250), 0, 10)`                                     |
| `timeRemainingSec` | ステージ3のクリア時の残り秒数（切り捨て）。送信された `durationMs` と突き合わせて検証されます |

unit は他のメトリクスで上限が決まるため（`comboUnits ≤ nearMissCount × 9`）、水増しした
値は検証で弾かれます。

### ランク

各ステージと合計に S / A / B / C が付きます。閾値は `shared/game-rules/v3.json` の
`stages.<id>.rank` にあります。合計のランクは各ステージ閾値の合計と比較します。

## ステージ1: 遅刻回避

### 内容

主人公は私道を自動で走り続けます。プレイヤーは左右の移動だけを操作し、他の生徒を避けながら
校門を目指します。縦スクロール。

### 操作

**画面のどこでも、指を左右にドラッグ。** 主人公は指の**絶対位置ではなく移動量**に追従します。

これは重要な選択です。絶対位置だと、操作している自分の親指がキャラクターを隠してしまいます。
相対ドラッグなら指を置き直しても瞬間移動せず、画面下部を持っても真ん中を持っても同じように
操作できます。

### 障害物（6種類）

| 種類                 | 挙動                                 |
| -------------------- | ------------------------------------ |
| 普通に歩く生徒 A / B | まっすぐ。配色違い                   |
| 小走りする生徒       | 速い（相対速度が大きい）             |
| ふらふら歩く生徒     | 左右に振れ続ける                     |
| 急に進路を変える生徒 | 近づいたら一度だけプレイヤー側へ寄る |
| 二人組               | 横幅が広い                           |
| 三人組               | さらに広い。道の6割を塞ぐ            |

出現頻度・速度・大きさは `src/config/stages/late.ts` の `obstacles` にあります。行を足せば
種類が増えます。

### 得点

| 事象                                         | 点         |
| -------------------------------------------- | ---------- |
| ニアミス（すれ違い時の横の隙間が 74px 以内） | +130       |
| コンボ（連続ニアミス、1回あたり最大4 unit）  | +20 × unit |
| 衝突                                         | −280       |
| 校門到達                                     | +1000      |
| 残り時間                                     | +80 / 秒   |

**ただ避けるだけではほとんど点が入りません。** 高得点には、ぶつかる寸前を通り続ける必要が
あります。

### 衝突したとき

ゲームオーバーにはしません。一時的に減速し（0.42倍・0.9秒）、減点・振動・SE・軽い画面
シェイク・無敵時間（0.85秒）が入ります。無敵があるのは、人混みに突っ込んだときに連続で
減点され続けないようにするためです。

### 終了

規定距離を走ると校門が流れてきて、到達で終了します。到達前に35秒経過した場合も終了し、
到達ボーナスは入りません。

## ステージ2: 羽沢パン購入RTA

### 内容

画面上部に注文（例: 「カレーパン」）が表示され、棚から同じ商品をタップします。1プレイ6〜10問。

### 難易度の作り方

問題が進むにつれて2つの軸で難しくなります。

1. **棚に並ぶ商品が増える**（4個 → 12個）
2. **同じ family の紛らわしい商品が混ざる**

family が同じ商品の例:

| family   | 商品                                         |
| -------- | -------------------------------------------- |
| curry    | カレーパン / 辛口カレーパン                  |
| melon    | メロンパン / ホイップメロンパン              |
| an       | あんパン / うぐいすあんパン                  |
| sandwich | カツサンド / たまごサンド / ハムチーズサンド |

つまり後半は「絵が違うものを探す」ではなく「名前をきちんと読む」ゲームになります。これが
RTA としての腕の差になる部分です。

商品名は画像の下にも表示されます。仮素材でも遊べるようにするためであり、音を切っていても、
色が見分けにくくても遊べるようにするためでもあります。

### 得点

| 事象         | 点                                                   |
| ------------ | ---------------------------------------------------- |
| 正解         | +220                                                 |
| 速度ボーナス | +85 × unit（最大10 unit。2.5秒以内なら段階的に加算） |
| コンボ       | +60 × unit（1回あたり最大5 unit）                    |
| 誤答         | −280、コンボリセット                                 |

さらに、合計点に **8 ÷ 出題数** を掛けて正規化します。出題数は6〜10問のランダムなので、
正規化がないと「10問引いた人」が「6問引いた人」の約1.9倍のスコアになってしまい、
ランキングが運で決まってしまうためです。同じ1問あたりの実力なら、6問でも10問でも
まったく同じスコアになります（`tests/scoring.test.ts` で検証）。

誤答したパネルは 0.26 秒タップできなくなります。連打で総当たりされないためです。

### 商品を追加する

ゲームロジックの変更は不要です。手順は [ASSETS.md](ASSETS.md) の「パンを追加する」にあります。
`BREAD_ITEMS` に1行、マニフェストに1行です。

## ステージ3: 放課後ステルス

### 内容

放課後の校内を見下ろし型 2D で移動し、**先生に見つからないように目的地を回って昇降口から
脱出する** タイムアタックです。

ゲームの中心にあるのは一貫してひとつの判断です:

```text
           ┌── 中央連絡通路（短い・先生が2人）──┐
  昇降口 ──┤                                  ├── 北棟の目的地
           └── 東/西の外周（1.5倍長い・安全）──┘
```

短いルートは速いが危険。遠回りは安全だが、タイムボーナスを失う。1回のプレイで 3 回ほど
この選択をします。

### 操作

| 操作           | 結果                                                     |
| -------------- | -------------------------------------------------------- |
| 画面をドラッグ | 指を動かした**方向**へ移動。動かした量が速度（上限あり） |
| 何もしない     | 止まる                                                   |

指の**絶対位置**は使いません。指が主人公を隠さず、画面のどこで握り直しても主人公が飛ばない
ためです。斜め移動は正規化してあるので、斜めが速いことはありません。判定は
`src/game/core/DragVector.ts` に切り出してあり、単体テストされています。

仮想十字キーは出しません。画面下部 30% は「ここに指を置けばマップが隠れない」ことを示す
だけの帯で、操作をそこに制限するものではありません。

### 目的地

1プレイで **目的地 2 箇所 + 昇降口** を回ります。近づくと自動で回収され、ボタンはありません。
最後の目的地を取ると `EXIT!` が出て、脱出フェーズになります。

目的地の順番は `src/config/stages/teacher/maps/` の **ミッションパターン**（現在 3 種類）から
seed で選ばれ、うち 1 箇所だけが代替候補に差し替わります。パターンを覚えれば強いが、毎回
目的地リストは見る必要がある、という配分です。

### 先生

各先生は**決められた巡回ルート**を A→B→C→B→A と往復します。行き先を乱数で決めることは
ありません。乱数が触るのは「その場で何秒立ち止まるか」「振り返るかどうか」だけで、しかも
すべて設定された min/max の範囲内・run の seed 由来です。**観察すれば読めること**が
このステージの前提です。

| 状態          | 内容                                       |
| ------------- | ------------------------------------------ |
| `PATROL`      | ルートを歩く                               |
| `WAIT`        | 指定地点で立ち止まる（周囲を見回すことも） |
| `TURN`        | 立ち止まって振り返る                       |
| `INVESTIGATE` | 見かけた地点まで様子を見に行く             |
| `RETURN`      | ルートへ戻る                               |

4 タイプ（要件15）:

| タイプ    | 性格                     | 危険なところ                                     |
| --------- | ------------------------ | ------------------------------------------------ |
| `normal`  | 一定ルートを普通に巡回   | いちばん読みやすい                               |
| `stander` | 特定地点で数秒立ち止まる | 止まっている間、首を左右に振る                   |
| `looker`  | ときどき振り返る         | 後ろについて歩くと急に視界に入る                 |
| `roomer`  | 部屋から時々出てくる     | 直前にいた場所にいない。出てくる前にドア音が鳴る |

巡回に大規模な経路探索は使っていません。**マップに書いた waypoint グラフ**の辺をたどるだけで、
様子を見に行くときも同じグラフ上を BFS でたどります（要件48）。

### 発見の仕組み

接触ではなく**視界**で判定します。

```text
      👨‍🏫          距離 → 角度 → 遮蔽 の順に判定
     ╱ │ ╲         壁の向こうは絶対に見えない
    ╱  │  ╲
```

視界に入っても即アウトにはなりません。検知メーターが溜まりきると発見です。

**この溜まる速さは距離で大きく変わります。**

| 位置               | 発見までの時間 |
| ------------------ | -------------- |
| 目の前             | 約 0.55 秒     |
| 視界のいちばん外側 | 約 2.2 秒      |

これは調整の結果です。当初は距離に関係なく一律 0.4 秒にしていたのですが、
`npm run balance` で測ると **一度でも見られたら必ず捕まる**（廊下で物陰まで逃げるには
1〜2 秒かかるため）状態になり、その結果「短いルートを選ぶ理由が一切ない」ゲームに
なっていました。距離を通貨にしたことで、

- 先生の真横を通る＝ほぼ即アウト
- 視界の端をかすめて走り抜ける＝見つかりはしないが PERFECT STEALTH は失う

という段階ができ、要件34 の「速いが危険」が成立しています。

視線が切れるとメーターは減ります。**角に逃げ込めば助かる**のはこのためです。

### 発見されたとき

ゲームオーバーにはしません。

1. 「おい！」を約 1.1 秒表示
2. 1.5 秒間その場で動けない（＝実質の時間ペナルティ）
3. 直前の安全な地点へ少し戻される（**最大 620px**。要件22 は「直前のチェックポイントへ」
   ですが、それだと 2000px の行程が丸ごと無駄になり、測定したところ短いルートを選ぶ
   メリットが完全に消えていたため、戻す距離に上限を付けています）
4. `−950` 点、さらに「無発見ボーナス」と「PERFECT STEALTH」を失う

合計すると 1 回の発見はおよそ **2500〜3000 点**の損です。プレイは続けられますが、
上位を狙うなら 1 回でもかなり不利、という要件23 の意図どおりの重さです。

### 得点

| 事象                       | 点                           |
| -------------------------- | ---------------------------- |
| 目的地に到達               | +250 × 箇所                  |
| 脱出成功                   | +1600                        |
| **タイムボーナス**         | **+220 × （残り秒数 − 30）** |
| 一度も捕まらずクリア       | +800                         |
| 一度も見つかりかけずクリア | +1000（PERFECT STEALTH）     |
| 先生のすぐ脇を通過         | +170（CLOSE CALL・上限10回） |
| 発見される                 | −950                         |

**得点の中心はクリアタイムです**（要件30）。上の式で分かるとおり、上手いプレイの得点の
7 割前後はタイムボーナスです。

- **待てば安全。しかし待つほど確実に損をする。** 要件33 はこの一行で満たしています。
- 残り時間のうち **30秒ぶんは無得点**です。90 秒という制限は「詰まっても終われる」ための
  安全網であって目標ではないので、そこを一律に払うと「とりあえずクリアした人」全員に
  同じ大きなボーナスが乗り、速さが評価されなくなります。

`perfectStealth` はリザルト表示用に送られますが、**ボーナスの判定には使いません。**
サーバーは発見回数・目撃回数から自分で導出するので、フラグを書き換えても 1 点も増えません。

CLOSE CALL は「先生1人につき、目的地1区間あたり1回だけ」しか入りません。先生の周りを
ぐるぐる回って稼ぐことはできず、稼ぐには先へ進むしかありません（要件32）。

### マップを差し替える

校内の形は**データ**です。`src/game/stages/teacher/TeacherScene.ts` は特定のマップを
知りません。

```text
src/config/stages/teacher/
  mapTypes.ts              型定義
  maps/komabaPlaceholder.ts  ← 仮の校舎（このファイルを差し替える／隣に足す）
  maps/index.ts            登録と DEFAULT_MAP_ID
```

マップは軸平行な矩形だけでできています。

| 要素          | 意味                                                   |
| ------------- | ------------------------------------------------------ |
| `bounds`      | 校舎全体の外周                                         |
| `areas`       | 歩ける区画。床の見た目と部屋名（当たり判定ではない）   |
| `walls`       | **通れない・見通せない**ブロック。壁も遮蔽物もこれ一つ |
| `waypoints`   | 先生の巡回グラフの頂点                                 |
| `edges`       | その辺（壁を跨いでいないことをテストが検証します）     |
| `checkpoints` | 目的地と出口                                           |
| `patrols`     | 誰がどのルートをどう歩くか                             |
| `missions`    | 目的地の並び（パターン）                               |

実際の駒東の資料が来たら、同じ形式のファイルを 1 つ書いて `DEFAULT_MAP_ID` を向けるだけです。
`npm test` が、壁に埋まった目的地・壁を突っ切る巡回ルート・出口に着かないミッションを
すべて弾きます。

## 難易度の調整

| 調整したいもの               | 触る場所                          |
| ---------------------------- | --------------------------------- |
| 点の配分・ランク閾値・上限値 | `shared/game-rules/v3.json`       |
| 障害物の出現頻度・速度       | `src/config/stages/late.ts`       |
| 問題数・選択肢の増え方       | `src/config/stages/bread.ts`      |
| 先生の速度・視界・検知の速さ | `src/config/stages/teacher/`      |
| 校内の形・巡回ルート・目的地 | `src/config/stages/teacher/maps/` |
| 全体の難易度倍率             | `.env` の `VITE_DIFFICULTY_SCALE` |

### バランスを測る

数値を変えたら推測せずに測ってください。

```bash
npm run balance
```

`scripts/balance-report.ts` が、**実際の**校内マップ・巡回AI・視界判定・検知メーター・
問題生成・設定値・スコア式を使って、4段階の腕前のプレイヤーを各400回シミュレートし、
スコア分布とステージごとの寄与率を出します。モデル化しているのはプレイヤーだけです。

狙い:

- どのステージも合計の 30〜40% 程度を占める（1つのステージが支配しない）
- average が B、good が A、expert が S になる

> このツールで見つかった問題:
>
> - 先生ステージ（旧仕様）が合計の70%を占め、誰でもSランクになっていた
> - パンの出題数が6問か10問かでスコアが1.9倍違っていた
> - ステルスステージの初版は、一度見られたら必ず捕まる＝**短いルートを選ぶ理由が
>   存在しない**状態だった（検知速度を距離に応じたものへ変更）
> - 発見時に直前のチェックポイントまで丸ごと戻す設計が、同じく速いルートの価値を
>   消していた（戻す距離に上限を追加）

`shared/game-rules/v3.json` を変更したら:

1. `shared/game-rules/score-fixtures.json` の期待値を更新する
2. `npm test` と `cd backend && composer test` の両方を通す
3. **既存のスコアが動くような変更なら、必ず新しい `vN.json` を作って `configVersion` を
   上げる**（`backend/.env` の `CONFIG_VERSION`、`RuleSet::CURRENT_VERSION`、
   `src/config/rules.ts` の import を合わせる）

   ランキングは現在の `configVersion` のスコアだけを表示します。古い世代のスコアは
   削除されずに残りますが、別世代として扱われます。バージョンを上げずにバランスを
   変えると、旧スコアと新スコアが同じ表に並んで比較不能になります。
